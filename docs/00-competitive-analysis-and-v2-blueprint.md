# 竞品深度对标与 HyperDesign 2.0 蓝图

> 对标对象：`mechanical-ai-knowledge-platform`（上海博锐机器人 / Gitee，MIT）
> 参考场景：第三届"兴智杯"全国人工智能创新应用大赛 · 解决方案赛
> 本文档回答三个问题：他强在哪 → 我们差在哪 → 2.0 怎么把两者的强项焊在一起

---

## 一、对标对象的真实水平（不是"套壳"，是工程体系）

仓库结构：`backend`（49 个 service / 20 个 API 模块 / tool worker）+ `frontend`（Vue3 + Element Plus，13 个视图）+ `solidworks-plugin`（C# .NET 4.8）+ 4 个 `m0-*-poc` + `docs/ai-design-platform-spec`（17 份编号规格文档）+ `docs/handbook`（H01–H06）。

**它的强项是"把 AI 关进工程的笼子里"**，具体体现在五个层次的抽象：

| 层次 | 他的做法 | 与我们 v1 的差距 |
|---|---|---|
| **Agent 语义** | Agent = 有边界的决策/协调单元，明确"不负责计算、不负责 CAD 内核、不负责求解"；输出统一信封 `{status, confidence, assumptions, warnings, citations, result, next_action}`，status 仅四值（completed / needs_input / needs_review / failed） | 我们的阶段脚本直接调用 LLM 拿自由文本/JSON，**没有状态语义、没有 assumptions/warnings 披露** |
| **Skill 语义** | 可版本化、可允许列表化的确定性技能（公式计算、CAD 操作），Agent 只能调用 `allowed_skills` | 我们的能力以"脚本 + 提示词"形式存在，**不可枚举、不可版本化、无法被 Agent 按权限调用** |
| **Harness 语义** | 约束/验证/准入框架，规则带 `severity(info/warning/error/critical)`、`actual/limit/unit`、`citation`、`suggested_action`、`blocking`；聚合结论四值含 `invalid`；禁止用户表达式，只允许受控算子集 | 我们的 DFM 检查是**硬编码 if-else**，不产出结构化裁决、无引用溯源、无法按严重级分层 |
| **CAD-IR** | 智能体与 CAD 引擎之间的**受控中间表示**：`parameters/features[]/semantic_refs/outputs`；特征带 `depends_on/targets/on_failure`；用**稳定语义引用**（`segment:s3:cylindrical_face`）替代 `Edge1/Face3`；**明文禁止 `execute_script`**；引擎能力声明 + `CAD_CAPABILITY_UNSUPPORTED` | 我们 v1 **正是"LLM 生成 Python 脚本 → 直接在 freecadcmd 里执行"**，这既不可审计、也不能换内核，是他明确规避的反模式（也是评审最容易质疑的安全点） |
| **工作流** | 持久化运行 + 节点类型（计算/CAD/CAE/审批）+ SSE 事件（带单调序号、按 task_id+sequence 去重补拉）+ 重试 + 人工审批节点 | 我们是**线性脚本 + 日志文本**，无事件流、无审批节点、无断点续跑 |

工程纪律上他还有三样东西值得抄：**PoC 门禁**（进业务开发前必须通过 7 条硬门禁）、**观测关联字段**（request/project/task/workflow/node/agent/tool/version 八级 ID）、**编号规格文档 + archive 决策记录**（v1-decisions.md / troubleshooting.md / handover-context.md）。

## 二、他的四个结构性软肋（我们的机会）

1. **域太窄且强模板化**：只有"阶梯轴"和"二级减速器"两类零件，本质是**参数表驱动**（`segments[]` 的 length/diameter），没有从造型概念出发的设计。它解决不了"产品长什么样"这个上游问题。
2. **无生成式造型链路**：没有 2D 概念发散、没有图像→3D 重建、没有造型风格探索。评委看到的界面再漂亮，造型能力仍是人给的。
3. **无物理级 DFM**：他的 Harness 里有"几何可行性/最小圆角/加工可达性"这类规则，但没有**从网格实测壁厚/拔模**的能力——即没有"射线测厚"这类物理证据，DFM 仍是规则书式判断。
4. **无自进化**：没有偏好数据飞轮、没有微调、没有基准回归守门员。模型能力是静态的。
5. **自承短板**：他现场竞品分析页自己写了——路线一（传统 CAD 二次开发）"AI 适配 CAD 人类工具，缺乏自主能力"；路线二（轻量代码参数化 CadQuery）"仅支持基础几何体参数化、无工程制图规范、无公差/基准/关联、无干涉校验物理逻辑"。这两条正是我们的差异化靶心。

## 三、我们 v1 的真实短板（必须承认）

| 维度 | v1 现状 | 风险 |
|---|---|---|
| 架构可审计性 | 七阶段线性脚本 + 自由文本日志 | 评审问"你们的 Agent 边界在哪、失败如何升级"时答不上结构 |
| CAD 生成方式 | LLM 直接写 FreeCAD Python 并执行 | 安全事故/不可复现/换不了内核 |
| 交互面 | 单页 Three.js 审阅台（只有 3D + 勾选） | 与对手"三栏 Studio + 工作流画布 + 审批"相比显得单薄 |
| 知识资产 | 6 条工艺规范嵌入式检索，无入库/OCR/分类/RBAC | "知识平台"这条线几乎缺失 |
| 验证闭环 | 几何校验 + DFM 硬判（无 CAE、无工程计算） | 缺"强度/刚度/安全系数"这类工程结论 |
| 可观测 | 文本日志 | 无 trace/关联 ID，无法做量化成效归因 |

## 四、2.0 的定位：把"生成式造型深度"装进"平台化工程骨架"

一句话：**v1 是"能出活的引擎"，2.0 是"能被工厂验收的系统"**。

### 4.1 分层架构（新增层用 ★ 标注）

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ ★ L5 交互层  HyperDesign Studio（零构建单页：工作台三栏 + 工作流画布 + 审批）    │
├──────────────────────────────────────────────────────────────────────────────┤
│ ★ L4 编排层  Workflow Engine（持久化 DAG / 节点状态机 / SSE 事件 / 重试 / 审批） │
│ ★        Agent Layer：Supervisor + requirement / planning / concept / cad /    │
│                       cae / drawing / verification / delivery（统一输出信封）   │
├──────────────────────────────────────────────────────────────────────────────┤
│ ★ L3 约束层  Harness 规则引擎（工艺铁律 2.4/1.44/1.8° 为声明式规则，带引用溯源）│
│ ★        Skill Registry（版本化确定性技能：检索/测厚/IR构建/CAE/制图/计算）      │
├──────────────────────────────────────────────────────────────────────────────┤
│ ★ L2 表示层  CAD-IR（受控中间表示 + 引擎能力声明 + 语义引用 + 禁止 execute_script）│
│              引擎适配器：FreeCAD/OCCT（主通道）· CadQuery（备查）· SolidWorks（通道二）│
├──────────────────────────────────────────────────────────────────────────────┤
│ L1 能力层（v1 复用） 工艺 RAG · FLUX.2 概念发散 · TRELLIS 白模 · Blender 对齐      │
│                     · 射线测厚/拔模扫描 · OCC 校验 · HLR 四视图 · 国标 DXF/PDF     │
│ ★                   · CAE（Gmsh 网格 + CalculiX 求解 + 应力/位移云图）           │
│ ★                   · 工程计算（轴强度/刚度/安全系数）                          │
├──────────────────────────────────────────────────────────────────────────────┤
│ ★ L0 资产层  知识资产（入库/解析/OCR/表格抽取/混合检索/RBAC）· 设计资产版本树     │
│              · 事件与审计 · 观测关联 ID（8 级）                                │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 吸收清单（逐条落地，不做"致敬式"复刻）

| 吸收项 | 2.0 落地形态 | 相对他的差异化 |
|---|---|---|
| Agent 输出信封 | 全部 Agent 强制返回 `{status, confidence, assumptions[], warnings[], citations[], result, next_action}`，非法即 `invalid` | 我们的 citations 直接指向**工艺规范原文条款 + 几何实测证据** |
| Skill Registry | `skills/*.py` 注册表：`key@version`、输入输出 Schema、超时、幂等；Agent 只能经允许列表调用 | 技能里含他完全没有的 **`dfm.ray-cast` / `concept.flux` / `mesh.align` / `evolution.dpo`** |
| Harness 规则引擎 | 规则 YAML：`ruler_id/severity/expr/limit/citation/blocking`；聚合四值；**工艺铁律 2.4mm/1.44mm/≥1.8° 成为可审计规则条目** | 我们的规则带**物理证据**（p10 壁厚实测 1.51mm vs 限值 2.4mm），他的规则只有阈值判断 |
| CAD-IR | JSON Schema + 解释器 + 双引擎适配器 + 能力声明 + 语义引用 | 我们的 IR 直接由**白模切片锚点**生成（`geometry_anchor` 特性类型），他的是人手填参数 |
| 工作流事件 | 事件流带 `seq`，SSE 推送，前端按 `task_id+seq` 去重补拉；节点含 `approval` 类型 | 我们的审批节点前挂**DFM Harness 硬门禁**，不达标不允许提交审批 |
| 知识资产平台 | 文档入库（PDF/DOCX/表格/OCR）+ 混合检索（BM25+向量）+ 引用溯源 + RBAC | 我们的检索结果直接驱动**规则注入与提示词约束**（而不是只回答问答） |
| PoC 门禁 | `docs/poc/` 七条门禁报告，全部可复跑 | 我们的门禁里加"**生成式链路可复现性**"（同一 seed 同一图）与"**守门员回归**" |
| 观测 ID | 8 级关联 ID 贯穿 trace，前端显示每节点耗时/重试/证据 | 我们额外记录**模型版本 + 提示词哈希 + 采样参数**，保证可复现 |

### 4.3 反超点（评委最吃什么）

1. **生成式造型 → 可制造实体 的完整闭环**（他完全没有）：概念图 → 白模 → 毫米锚点 → CAD-IR → 实体 → 图纸。
2. **物理级 DFM 证据链**：500 条法向射线测厚 + 拔模角场 + 水密性，把"能不能开模"变成数据。
3. **自愈闭环 + DPO 飞轮 + 基准守门员**：出错代码自动修复并沉淀为偏好样本；新模型必须过回归才允许切流（他无模型迭代能力）。
4. **国标制图直连**：GB/T 图层 + 1:1 激光 DXF + A3 300dpi PDF（他自承"无公差/基准/关联/工程制图规范"）。
5. **零构建、全离线**：Studio 单页无 npm 依赖、可 U 盘拷走；模型权重全本地，数据不出内网。

## 五、按评审四维的攻防策略

| 维度（权重） | 他的强项 | 2.0 的攻法 | 需要的证据 |
|---|---|---|---|
| 先进性 25% | 多 Agent + Skill/Harness + CAD-IR 抽象完整 | 保留同等抽象严谨度，并在"生成式 + 物理验证 + 自进化"三处形成**架构级独到性**；给出 CAD-IR 与 Harness 的正式规范文档 | 规范文件 + 代码行号级引用 + 架构图 |
| 场景价值与应用成效 30% | 阶梯轴/减速器算例 | 用**同一条流水线**跑两个真实产品（传感器外壳 + 轴类零件），给出**端到端耗时、DFM 拦截率、图纸一次通过率、人工工时对比** | 实测表格 + 复跑脚本 + 原始日志 |
| 落地可行性 25% | 单机 Windows、SQLite、离线可跑 | 离线单机 16GB 显存可跑通；CAD-IR 可换内核（FreeCAD/SolidWorks）；STEP/DXF 标准格式交付；RBAC + 数据不出内网 + 无云依赖 | 部署清单 + 依赖冻结 + 断网演练记录 |
| 完整性表达 20% | 文档体系（H01–H06 + 17 份 spec） | 申报书严格按模板（仿宋GB2312五号、≤3万字、外文首现全称+缩写、引用注明出处）+ 编号规格文档 + 分镜完整的演示视频 + 附录二维码 | 申报书 docx + PDF + 视频 + 仓库 |

### 5.1 量化成效指标（必须由脚本产出，不能口算）

| 指标 | 采集方式 | 用途 |
|---|---|---|
| 端到端交付时长（概念→STEP+图纸） | 工作流事件流时间戳 | 场景价值核心数字 |
| 各节点耗时分解 | 节点事件（agent/tool/model 三段） | 说明瓶颈与优化空间 |
| DFM 拦截率 | Harness 裁决统计（failed/passed） | 证明"不可替代性" |
| 图纸一次通过率 | 校验脚本（图层/尺寸/包络） | 证明交付质量 |
| 自愈轮次分布 | CAD-IR/CAD 修复记录 | 证明鲁棒性 |
| 模型迭代守门员结果 | 基准回归 JSON | 证明自进化可控 |
| 人工工时对比 | 与工程方标定（假设需标注） | 商业价值，须标注为"假设/待验证" |

## 六、实施路线（M0–M6，每阶段有门禁）

| 阶段 | 内容 | 门禁 |
|---|---|---|
| **M0** | CAD-IR Schema + 解释器 + FreeCAD 适配器；Harness 引擎 + 工艺铁律规则 | 同一 IR 两次重建，包围盒/体积误差 < 0.1%；`execute_script` 被拒绝 |
| **M1** | Agent 层 + Skill Registry + 输出信封校验 | 每个 Agent 至少 6 类异常用例通过 |
| **M2** | Workflow Engine + SSE 事件 + 审批节点 + 断点续跑 | 断线重连不丢终态；审批驳回可回退 |
| **M3** | Studio 前端（三栏 + 工作流画布 + 3D 视窗 + 对话 + 审批） | 端到端手工走通一遍并录屏 |
| **M4** | CAE（Gmsh+CalculiX）+ 工程计算 Skill | 基准算例与理论解趋势一致 |
| **M5** | 知识资产平台（入库/OCR/混合检索/RBAC） | 20 份文档入库，检索命中率与引用正确率达标 |
| **M6** | 参赛材料（申报书 docx + PDF + 视频 + 仓库） | 按模板逐项自查表通过 |

## 七、与 v1 的关系

- **v1 保留为能力内核**（`D:\hyperdesign`），2.0 通过 Skill 适配器调用其脚本（`phase2/3/5/6` 的成熟实现），不重写、不推翻。
- **2.0 新增平台层**（`D:\hyperdesign2`）：CAD-IR、Harness、Agent、Workflow、Studio、CAE、知识资产、观测。
- 两仓通过 `manifest.json` 兼容层对接：2.0 的 Design Contract 是 v1 manifest 的超集（新增 `cad_ir`、`harness_verdicts`、`agent_envelope`、`events`、`trace_ids`）。
